## 1. 현행 [후] 입력 경로 지도 (실측)

```
(A) 화면 수동 카드            (B) 가입제안서 PDF 업로드
  CoverageRemodel 제안 입력       POST /coverage/proposals/parse
        │                                  │
        │                     proposal_parser.parse_proposal_pdf
        │                       ├ _detect_profile → proposal_registry.ProductProfile
        │                       ├ PROPOSAL_RULES(23룰) 키워드 매칭 → 담보명·금액
        │                       └ fallback_coverages(프로파일별 기본값)
        └──────────────┬───────────────────┘
                       ▼  plan.proposals[]
   compare.build_after_analysis (server)  ·  buildAfterResult (client 미러)
                       ▼
   proposal_contracts(신규 계약 P1·P2…) + proposal_values{담보:{P1:금액}}
                       ▼
   carry_coverage_row(row, kept_ids, known_ids, extra_values=proposal_values[담보])
     ├ 일반 행: keep/cancel 필터 + '?' 이월 + ★extra 병합 후 재집계
     └ overview 행: 귀속돼 있으면 일반 경로(259), 아니면 합계 + extra 가산
                       ▼
   export_excel [후] 회사 열(252) / export_pdf ③ 신규가입 제안서 섹션
```

### 실측 확인 사항
- **레지스트리 규모**: `PROPOSAL_RULES` **23룰** + `ProductProfile` 소수(키워드·fallback 보유).
  등록 상품 밖 제안서는 담보 채집이 비거나 부분적이다 → 카탈로그 1-1의 "5상품 한정" 상태.
- **[후] 신규 골격 열(252)**: 제안 계약이 payload에 **있으면** 일반 회사 열로 전개되고,
  **없으면** `신규 설계 반영 대상` 빈 열 1개만 표시(`has_proposal` 분기). 즉 렌더는 이미
  제안 트랙을 기다리는 상태이며, 데이터만 채우면 자동으로 열이 생긴다.
- **246 이월 모델과의 접점**: 제안 금액은 `extra_values`로 `carry_coverage_row`에 들어가
  **기존 이월분과 합산**된다(`AGG_SUM`은 더하고 `AGG_REP`은 max). 즉 신규 트랙은 이월 규칙을
  바꾸지 않고 **값만 추가**하는 구조 — 이번 설계도 이 계약을 유지한다.
- **`?`/미확인과 무관**: 제안 계약은 `P1`,`P2`… 별도 키라 253의 계약 미확인 버킷과 충돌하지 않는다.

## 2. 샘플 없이 확정 가능한 설계

### 2-1. 신규 계약 데이터 스키마
```jsonc
{
  "proposal_id": "P1",              // 없으면 순번으로 부여(현행 compare 로직과 동일)
  "insurer": "○○화재",              // 필수
  "product": "무배당 ○○건강보험",     // 필수(표지·시트2 상품명 행에 그대로)
  "monthly_premium": 50000,          // 필수(원) — 월납 합계·차액·20년 환산(261)에 사용
  "pay_months": 240,                 // 선택(없으면 총납입 미산출 — 현행 paid_total 규칙 준수)
  "maturity": "100세",               // 선택
  "pay_cycle": "월납",               // 선택(일시납이면 월납 합산 제외 — 234 규칙)
  "coverages": [                     // 담보별 금액(원)
    { "kb_name": "암진단금", "amount": 30000000, "group12": "암", "agg": "sum" }
  ]
}
```
- **40행 매핑 규칙**: `kb_name`은 반드시 `constants.KB_COVERAGES`의 정식명이어야 시트2 35행 +
  Y/N 5행에 자동 안착한다. 매칭 실패분은 **버리지 말고** `기타`로 보존해 시트2 하단 부록에
  노출한다(248 "양식 밖 담보 누락 0" 계약 준수).
- Y/N 5행은 별도 입력이 아니라 **원천 담보(운전자 4·배상 1·실손 4)를 채우면 파생**된다
  (254 `compute_yn_flags.by_company`가 제안 계약 키에도 동일 적용).

### 2-2. 업로드 → 파싱 → [후] 반영 흐름
1. 기존 KB 보장분석서 업로드(`/coverage/analyze`)로 **[전]** 확정 — 변경 없음.
2. 가입제안서 업로드(`/coverage/proposals/parse`, `doc_type=proposal`) → `plan.proposals[]` 초안.
3. 화면에서 설계사가 **검토·수정**(파싱 신뢰도가 낮은 항목은 값이 비어 있고 수기 보완).
4. "전후 비교 계산" → `buildAfterResult`(클라이언트) 또는 `build_after_analysis`(서버)로 [후] 산출.
5. 엑셀/PDF 내보내기 — 252 회사 열·254 Y/N·261 20년 차액이 자동 반영.
- ★**KB 업로드 동선과의 관계**: 완전히 분리된 두 업로드다. 제안서는 [전]을 건드리지 않으며
  실패해도 [전] 분석은 유지된다(현행 엔드포인트 분리 구조 그대로).

### 2-3. 통합치료비류([후] 전용 3행) 채움 규칙
- 대상: `면역항암치료` · `암 주요치료비` · `순환계 치료비`(+`심혈관질환` 신담보).
- 현황: 정본 2건 모두 **[전] 원문 0건**(262 재실측 `enrolled=False`) → 246 설계상 **[후] 전용 자리**.
- 규칙(확정 가능): 제안서에서 해당 담보가 채집되면 **그대로 [후] 값으로 기입**하고,
  [전]은 계속 공란(미가입)으로 둔다. 시트2에서 이 3행은 이미 `NEW_PLACEHOLDERS`로
  `[신규 설계 반영 대상]` 표기가 붙어 있어 **오독 방지 장치가 선행 완비**돼 있다.
- ★확정 불가(**샘플 필요**): 각 회사가 이 담보를 어떤 문구로 쓰는지(예: "암주요치료비" vs
  "항암주요치료비" vs 특약명 단독). 키워드 룰은 실 문서 없이 만들 수 없다.

### 2-4. 회사별 양식 차이 대비 파서 구조 — 어댑터 패턴 제안
```
proposal_parser.parse_proposal_text(text)
  ├ detect_adapter(text) → Adapter            # 회사·양식 지문(로고 문구·헤더·표 머리글)
  │    ├ KbAdapter        (기존 로직)
  │    ├ MeritzAdapter    ...
  │    └ GenericAdapter   (현행 키워드 룰 = 폴백)
  └ Adapter.extract(text) → {contract_meta, coverages[], warnings[]}
```
- **공통 계약**: 어댑터는 §2-1 스키마만 반환하고, 40행 매핑·집계·이월은 기존 경로가 처리한다
  (어댑터가 집계에 관여하지 않게 해 회귀면을 좁힌다 — 256~258 "overview 전용 리졸버"에서
  검증된 방식).
- **선택 규칙**: 지문 매칭이 **유일할 때만** 전용 어댑터, 아니면 `GenericAdapter`
  (253/256의 "유일 매칭만 귀속" 원칙 재사용).
- **정직성**: 어댑터가 못 읽은 항목은 값을 지어내지 말고 `warnings`에 남기고 공란 →
  화면에서 수기 보완(현행 원칙 유지).

## 3. 샘플 확보 시 즉시 착수 가능한 단계 분할안

| 단계 | 내용 | 규모 | 검증 기준 |
| --- | --- | --- | --- |
| **S1** | 샘플 2~3사 구조 실측(지문·표 형식·담보 표기 사전) → 매핑표 문서화 | S | 실측표 산출·추측 0 |
| **S2** | 어댑터 골격 + `GenericAdapter`로 현행 로직 이관(동작 변경 0) | M | ★기존 23룰 회귀 0(값 diff 0) |
| **S3** | 회사별 어댑터 1개 추가(가장 빈도 높은 1사) | M | 해당 샘플에서 담보 채집률·금액 정확도, 타사 문서 무영향 |
| **S4** | 통합치료비 3행 키워드 룰 추가 | S | [전] 공란 유지·[후]만 채움, 정본 2건 무영향 |
| **S5** | [후] 회사 열 실렌더 검수 + 스모크 기준값에 제안 시나리오 추가 | S | `npm run smoke:coverage` 확장·FAIL 실증 |

- **선행 필수**: S1 이전에 **실 가입제안서 샘플**(회사 2~3사, 가능하면 동일 고객 건)이 필요하다.
  없이는 S3·S4가 추측이 되어 착수 금지.

## 4. 샘플 필요 항목 (확정 불가 — 명시)
1. 회사별 제안서 **지문**(어댑터 선택 근거가 될 고정 문구·헤더).
2. 담보 표기 사전 — 같은 담보의 회사별 명칭 변이.
3. 금액 표기 형식(만원/원·"1억"·표 셀 분리 여부) — 현행 `parse_korean_amount_to_krw` 커버 범위 밖 케이스.
4. 통합치료비 3행의 실제 문구(§2-3).
5. 납입기간·만기 표기 위치(현행은 프로파일 fallback 의존).
