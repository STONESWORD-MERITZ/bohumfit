### ★★패킷 전제와 방향이 반대다 — 실측으로 정정
패킷은 "액션 바가 네비를 덮어 **다른 탭으로 이동할 수 없다**"로 봤으나, 실제는 **그 반대**다.
- 두 요소의 `z-index`가 **똑같이 40**이라 승부는 DOM 순서로 갈린다. `Layout`은
  `<main>`(액션 바 포함) → `Footer` → **`MobileBottomNav`** 순서라 **네비가 나중에 그려져 위에 온다**.
- 그래서 **탭 이동은 지금도 된다**(탭 중심 히트 = 탭). 대신 **주 액션 버튼 56px 중 45px(80%)이
  네비에 덮여**, 버튼 아래쪽을 누르면 **버튼이 아니라 탭이 눌린다**.
- 결과적 증상: ①결과 화면의 **유일한 주 액션("카카오톡 문안 보기")이 사실상 눌리지 않고**
  ②누르려다 **의도치 않게 다른 화면으로 이탈**한다. 오조작 이탈이라 체감 심각도는 더 높다.
- ★이 정정은 해법 선택을 바꾼다(아래 Step 2).

### 액션 바가 제공하는 기능 (실측)

결과 본문 안에 있다. 즉 **액션 바 = 문안 시트 진입 버튼 1개**다.

### ★결과 화면에서 네비로 이동할 필요가 있는가
**있다.** 고지 결과는 확인 후 다음 행동(홈·보장분석)으로 넘어가는 화면이고, 실제로 **지금도
탭 이동이 되고 있다**(위 히트 테스트). 즉 네비를 없애는 선택은 **현재 되던 것을 빼앗는 후퇴**다.

## Step 2 — 해법 선택: **B안(세로로 쌓기)**

### 선택 사유 (Step 1 실측 근거)
- **A안(네비 숨김) 기각** — Step 1에서 **탭 이동은 현재도 정상 동작**함이 실측됐다. A안은 실제 결함
  (주 액션 80% 가림)은 없애지만 **되던 탭 이동을 없애는 기능 후퇴**다. 패킷의 A안 설명("탭 이동 불가")도
  같은 비용을 인정하고 있다.
- **C안(흐름 안 배치) 기각** — 액션 바의 유일한 기능이 문안 시트 진입인데, 결과 카드가 270으로
  1.3~1.4배 길어져 스크롤 끝까지 가야 닿는다. 주 액션 접근성이 크게 나빠진다.
- **B안 채택** — 두 기능(주 액션·탭 이동)을 **둘 다 온전히** 유지하는 유일한 안이고,
  "액션 바는 탭 바 위에 쌓는다"는 모바일 관례와도 일치한다.

### B안의 비용 (실측)
하단 고정 점유가 **141px(safe 0) / 175px(safe 34)** 로 커진다(640px 높이 기준 22% / 27%).
단 **콘텐츠는 가려지지 않는다** — 최하단 스크롤에서 마지막 줄과 액션 바 사이 여유 **43px**
(Layout `paddingBottom: 60 + safe + 2rem` + 셸 스페이서 80px가 이미 충분).
→ **여백 상수를 늘리지 않아도 된다**(불필요한 수정 0).

### 구현 방식
액션 바가 **네비의 실제 높이만큼 위로 올라간다**. 판정은 269b와 같은 **DOM 관찰**이다.
- ★**정적 오프셋(상수 60px)을 쓰지 않는 이유 2가지**:
  ① 실측 네비 높이는 **57px**이라 `BOTTOM_NAV_HEIGHT`(60) 기준으로 올리면 두 바 사이에
  **3px 틈**이 생겨 그 사이로 본문이 지나간다(재현 실측에서 확인).
  ② 네비는 시트(`role=dialog`)·분석 중(`data-analysis-busy`)에 **스스로 사라진다**. 상수 오프셋이면
  네비가 없는데도 60px 떠 있는 **빈 틈**이 생긴다.
  → `offsetHeight`를 그대로 쓰면 **세이프에어리어까지 이미 포함**되므로 ★이중 적용도 자동으로 없다.
- 세이프에어리어: 네비 위로 올라간 동안 액션 바는 `padding-bottom`을 **평상시 12px로만** 둔다
  (아래 네비가 인디케이터를 책임진다). 네비가 없으면 **기존 `.m-action-bar` 규칙 그대로**.
- ★네비가 없을 때의 마크업·스타일은 **현행과 완전히 동일**하게 유지한다(회귀면 0).
- ★`MobileBottomNav`는 **한 줄도 건드리지 않는다**(구조·탭·세이프에어리어·감지 조건 전부 무변경).

★**변경 파일은 `src/components/mobile/PrimaryAction.tsx` 하나뿐**이다.
- `useBottomNavHeight(enabled)` 추가 — `[data-testid="mobile-bottom-nav"]`를 `MutationObserver`로
  관찰하고, 있으면 `offsetHeight`(= 네비가 적용한 세이프에어리어까지 포함된 실제 높이)를 반환한다.
  높이 변화는 `ResizeObserver` + `resize`/`orientationchange`로 따라간다.
  `ResizeObserver`가 없거나 높이를 못 재면 `BOTTOM_NAV_HEIGHT`(60)로 폴백한다(겹침을 남기지 않는다).

  → 네비가 없으면 **인라인 스타일이 하나도 붙지 않아 현행과 완전히 동일한 마크업**이 나온다.
- `enabled = fixed`라 **흐름 안 배치(268a 시트)는 관찰조차 하지 않는다**.
- 진단용 `data-above-bottom-nav` 속성 1개 추가(네비 위에 있을 때만).
- ★`MobileBottomNav`·`Layout`·`DisclosureMobileShell`·`index.css` **무접촉**.

### 판단 기록
- ★**A안을 기각한 근거는 실측이다.** 패킷은 "네비로 이동할 수 없다"를 전제했지만, z-index가 같고
  네비가 DOM 뒤라 **네비가 위에 그려져 탭 이동은 이미 되고 있었다**. 실제 결함은 **주 액션이 눌리지 않고
  오조작으로 이탈**하는 것이었다. 그 상태에서 A안(네비 숨김)은 되던 기능을 없애는 후퇴가 된다.
- **상수 오프셋 대신 실제 높이 측정**을 택한 이유는 ①상수 60 vs 실측 57의 **3px 틈** ②네비가 시트·분석 중
  스스로 사라질 때 생기는 **빈 틈** 두 가지다. `offsetHeight`를 쓰면 세이프에어리어 이중 적용도 자동 해소된다.
- **`:has()` CSS 해법 미채택**: 한 줄로 끝나지만 iOS 15.4 미만에서 조용히 무효가 되고 jsdom에서
  검증할 수 없다. 269b가 세운 DOM 관찰 선례를 따르는 편이 테스트로 고정된다.
